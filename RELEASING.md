# Release procedure

Owner actions (require the owner's GitHub and Zenodo accounts). The Zenodo
webhook for this repository is already enabled; a GitHub release mints a new
version DOI automatically, under the same concept DOI.

1. **Tag and push:** `git tag v0.2.0 && git push origin v0.2.0`, then draft a
   release from the tag on GitHub. Zenodo archives the tree **as it stands at
   the tag** and mints the DOI within minutes.
2. **Nothing to write back.** `README.md` already cites the concept DOIs,
   which resolve to the newest version. Add a line only if a *version* DOI
   needs quoting somewhere.
3. **Order matters when other work is pending.** Whatever is in the tagged
   commit is archived under this repository's DOI, permanently. Tag first,
   merge unrelated lines of work afterwards.

## Pre-release checklist

- [ ] `make verify-all` green on a **fresh clone**, not just in place. Two
      absolute paths that resolved only on the author's machine were once
      shipped, and only a fresh-clone run would have caught them.
- [ ] every row of the README claim table has a working `make verify-*`
      target, and every file the README names exists
- [ ] every claim points at a statement that actually exists in the note at
      the cited number. v2.0 was assembled with three wrong cross-references,
      one of them to a result that was not in the note at all.
- [ ] `note/` builds: `tectonic -X compile note/measuring-the-moat.tex` —
      exit 0, no undefined references, no `??` in the extracted text
- [ ] `note/table_generated.*` regenerated by `python3 note/make_table.py`
      (never hand-edited), and its guards pass
- [ ] `git grep -n floor` reviewed: the word is used only for `E_δ(n)` itself
- [ ] no secrets: `git grep -I "sk-ant"` empty; no raw evolution logs tracked
- [ ] author line and copyright holder in `README.md` / `LICENSE` current

## Commands that dirty the working tree

Check `git status` before tagging: these rewrite tracked files as a side
effect, and the tag should not capture an accidental edit.

- `lib/dist2core/tests/test_n17_infeasible.py`, and hence
  `make verify-d2core-t2`, **overwrites** `data/t2_reprove_dist2core.json`,
  changing its `wall_time_seconds`. The committed value is the original run's;
  every other field is stable across re-runs.
- `experiments/beast_trail/shot_arc_test.py` rewrites its own results JSON.
  It has reproduced byte-identically so far, so this is normally a no-op.
- `python3 verify/check_hashes.py --write` regenerates `data/manifest.json`.
  It is safe — it walks `data/` and the witness subdirectories named in
  `WITNESS_DIRS` — but re-sorts keys, so expect a diff of moved lines.
